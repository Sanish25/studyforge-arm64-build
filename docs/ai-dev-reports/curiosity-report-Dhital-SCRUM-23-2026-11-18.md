### STUDENT

what does scope.py mean?

### AI

`scope.py` is the **gate that decides whether Pandu should help, ask for clarity, or refuse** — before (and sometimes after) tools run.

It answers: “Is this question something StudyForge should handle for *this* student’s course?”

### What it does

For each user message it produces something like:

- **`IN_SCOPE`** → continue into the tool loop  
- **`OUT_OF_SCOPE`** → **`abstain`** (no tools, polite refusal)  
- **`UNCLEAR`** → **`clarify`** (ask a follow-up, e.g. select materials)

It also can set **`needs_documents`**: if the ask needs course PDFs and none are selected → clarify “select/upload materials.”

### How (hybrid)

1. **Tiny fixed layer** (deterministic): JWT/ownership, empty message, a couple ultra-clear allows like “list my tasks.”
2. **Gemini classifier** for everything else (not a giant keyword list of “weather,” etc.).
3. **Post-tool evidence gate**: after retrieve/ask, if evidence is empty/weak → abstain/clarify instead of inventing.

### Why it exists

Without it, the agent would call tools (or invent answers) for roommate questions, weather, or cross-user asks. `scope.py` keeps Pandu on owned course work and makes refusals/clarifications explicit in the JSON `status`.

### What a “request-wide DB transaction” is
If Django’s `ATOMIC_REQUESTS` is on, every request is:

```text
BEGIN
  … entire view …
COMMIT  (or ROLLBACK on error)
```

That holds a DB connection/transaction open for the **full** request lifetime.

### Why that’s bad for Pandu
`run_pandu_turn` can take seconds (Gemini + tools). If that ran inside one request transaction:

- A DB connection stays checked out the whole time  
- Locks/rows can stay open longer than needed  
- A late failure can roll back work you already wanted kept (e.g. the PENDING question)  
- Under load, connection pool pressure goes up  

### What we do instead
In `urls.py`:

```python
transaction.non_atomic_requests(PanduAgentView.as_view())
```

So the view is **not** one giant transaction. Instead:

1. Short transaction: save user question (`remember_turn` / `start_question`) → commit  
2. **No transaction** while Gemini runs  
3. Short transaction: save assistant reply (or `mark_failed`)  

Same pattern as SCRUM-24’s conversation questions routes.

**DB writes = short. AI wait = outside any open transaction.**

### STUDENT

whats ATOMIC_REQUESTS

### AI

`ATOMIC_REQUESTS` is a Django DB setting.

When `True`, Django wraps **each HTTP request** in a database transaction:

- request starts → `BEGIN`
- view runs
- success → `COMMIT`
- uncaught exception → `ROLLBACK` (all DB changes from that request undone)

So the whole request is “all or nothing” for DB writes.

StudyForge’s Pandu/chat routes **opt out** with `transaction.non_atomic_requests(...)` so a long Gemini call isn’t sitting inside that open transaction. Small saves (question / reply) use their own short transactions instead.

Important distinction first: **`chatHistory.ts` does not save history.** It only turns saved DB rows into UI bubbles. Saving happens on the **backend** when you call the agent.

### End-to-end flow

```text
You type a message
    ↓
ConnectedCourseChat → POST /api/v1/agent/pandu/
    ↓
Backend saves USER question (PENDING)
    ↓
run_pandu_turn (Gemini + tools)
    ↓
Backend saves ASSISTANT reply (linked via reply_to)
    ↓
Frontend GET /conversations/{id}/messages/
    ↓
toChatMessage() (chatHistory.ts) → show in UI
```

### 1. Save (backend — durable)

In `views.py`, if `conversation_id` is present:

1. **`remember_turn(role="user")`**  
   Writes a `ConversationMessage` row: your question, status `PENDING`.

2. **`run_pandu_turn(...)`**  
   Agent answers (no long DB transaction held open).

3. **`remember_turn(role="assistant", reply_to=question_id)`**  
   Writes Pandu’s reply row linked to that question, with `text`, `citations`, `tool_trace`.  
   Question becomes `ANSWERED`.

If the agent crashes → question is marked `FAILED` (still kept so you can retry).

So history is **one row per turn** in `ConversationMessage`, all pointing at the same `Conversation`.

### 2. Load (frontend)

After the agent returns, `ConnectedCourseChat` calls:

```text
listConversationMessages(conversationId)
  → saved.map(toChatMessage)
  → setMessages(...)
```

On refresh / switch thread, it loads the same way. **DB is source of truth**; `sessionStorage` only remembers which chat + selected sources, not the messages.

### 3. What `chatHistory.ts` does here

| Function | Role in history |
|----------|------------------|
| `toChatMessage` | DB row → UI bubble (text, failed/pending, citations, tools) |
| `citationView` / `toolUses` / `agentToolUses` | Make sources/tools readable |
| `replaceMessage` | Used on **retry** to swap in saved Q+A without scrambling order |

### Mental model

- **Save** = backend `remember_turn` into Postgres  
- **Show** = frontend reload + `toChatMessage`  
- **New chat** = new `Conversation` (empty message list)  
- **Same chat** = more `ConversationMessage` rows under that conversation id

### AI

### What “bundle size” means

When you run `npm run build`, Vite packs your frontend into JS files browsers download. One of those is the **main chunk** — code needed early for the app shell.

Vite’s soft guideline is ~**500 kB**. Cross that and you get a yellow warning. Bigger file → slower first load on weak networks / phones. It’s a warning, not a broken build.

### Why `ChatMarkdown` is expensive

`CourseChat.tsx` does a normal import of `ChatMarkdown`, which pulls react-markdown, remark plugins, rehype-katex, and KaTeX CSS. Because of a **static** import, that stack can go into the **main** download even when the user never opens Pandu.

### “Lazy-load” in plain terms

**Today:** Buy groceries for the whole week the moment you leave the house — including fancy cooking tools you only need if you cook dinner.

**Lazy-load:** Leave the house with the basics. Only fetch the fancy tools **when you start cooking** (open chat / first assistant message).

In React that looks like `React.lazy(() => import("./ChatMarkdown"))` + `<Suspense>`.

Same UI once chat is open; **pages without chat don’t pay for markdown/KaTeX upfront**.

| | |
|--|--|
| **Gain** | Smaller first paint for non-chat routes |
| **Tradeoff** | Tiny delay the **first** time chat renders Markdown |
| **Not a bugfix** | Answers already work; this is performance polish |

### STUDENT

Vite’s soft guideline is ~500 kB is this standard?

### AI

It’s **Vite’s default warning threshold**, not a universal web standard.

Vite’s `build.chunkSizeWarningLimit` defaults to **500** (kB of the **uncompressed** chunk). Cross that and you get a yellow warning. You can raise or lower it in `vite.config` — it’s a nudge, not a fail.

**Industry-wise:** There is no single “must stay under 500 kB” rule. Performance budgets vary (e.g. mobile JS budgets are often discussed in the **100–200 kB compressed** range for critical path). Vite’s 500 kB is a convenient default for “this chunk is getting big,” not an RFC or Lighthouse hard fail.

So: **standard for Vite**, not a global law. Your ~864 kB warning is expected with markdown + KaTeX in the main chunk; gzip (~257 kB in Gaurav’s note) is what users actually download.

**Standard practice:** split heavy, route- or feature-specific code; keep the critical path small.

What teams usually do:

1. **Code-split by route/feature** — Dashboard loads dashboard code; chat loads chat (+ markdown/KaTeX) when you enter that screen. That’s normal for SPAs (React.lazy, dynamic `import()`, route-based chunks).
