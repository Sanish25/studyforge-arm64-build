### AI
A **VCN** (Virtual Cloud Network) is your own private network inside Oracle Cloud — like a home/office LAN, but virtual and isolated in OCI.

### What it gives you

Inside a VCN you get:

- **Private IP space** for your resources (e.g. `10.0.0.0/16`)
- **Subnets** — slices of that space (public vs private)
- **Gateways & routes** — how traffic leaves/enters (Internet Gateway, NAT, etc.)
- **Security lists / NSGs** — firewall rules (who can talk to whom on which ports)

Your VM does not float in “the open internet” alone. It sits **inside** this VCN, and the VCN decides what is reachable.

### Simple analogy

| Home network | OCI VCN |
|--------------|---------|
| Your router + Wi‑Fi | VCN |
| Devices (laptop, NAS) | Compute VM, later maybe more |
| Port forwarding / firewall | Security list / NSG |
| Public IP from ISP | Public IP on the VM (optional) |
| Private IPs like `192.168.1.x` | Private IPs like `10.0.x.x` |

### Why StudyForge needs one

For SCRUM-125 you need a VM that:

1. Has a **private** address inside OCI
2. Can be reached from the internet on **22 / 80 / 443**
3. Runs Postgres/Redis **only on the private side** (not open to the world)

The VCN is the container that makes that possible. Without it, you cannot place the instance and control those rules cleanly.

### Public vs private subnet (what the wizard creates)

- **Public subnet:** resources can have a **public IP** and use an **Internet Gateway** → good for your API VM (SSH + HTTPS).
- **Private subnet:** no direct public IP; outbound often via NAT → good later for DBs if you split them out. For our one-VM plan, Postgres/Redis run **on the same VM** and stay bound to localhost, so you mainly care about the **public** subnet for the instance.

### What a VCN is *not*

- Not a server  
- Not a database  
- Not storage  

It is only the **network + security boundary** those things plug into.

### What a subnet is

A **subnet** is a slice of the VCN’s IP range, plus a policy about who sits there.

Think of the VCN as a building, and subnets as floors:

```text
VCN  (the building)          e.g. 10.0.0.0/16
├── Public subnet            e.g. 10.0.0.0/24   ← “street-facing floor”
└── Private subnet           e.g. 10.0.1.0/24   ← “back-office floor”
```

Each subnet has:

1. **Its own CIDR** — a smaller IP block inside the VCN  
2. **Route table** — where outbound traffic goes (internet? only inside VCN?)  
3. **Security list / NSG** — firewall rules for resources in that subnet  

So a subnet is not a server. It is a **network neighborhood** with shared routing and firewall defaults.

---

### Public vs private subnet (what actually differs)

| | Public subnet | Private subnet |
|--|---------------|----------------|
| Can assign **public IP** to a VM | Yes | Usually no |
| Default route to **Internet Gateway** | Yes | No |
| Reachable from the internet | If public IP + open ports | Not directly |
| Typical use | Web/API servers, bastion/SSH | Databases, workers with no public IP |

**Public** does not mean “everything is open.” It means “this neighborhood is *allowed* to have a front door (public IP).” Your security list still decides whether 22/80/443 are open.

**Private** means “no front door.” Things there talk privately inside the VCN (and often go out via NAT for updates).

---

### Why the wizard still makes a private subnet

For a **split** architecture people later do this:

```text
Public subnet:  Nginx + Django VM   (has public IP)
Private subnet: Postgres VM / Redis  (no public IP)
```

Django reaches the DB over the VCN private network. Attackers on the internet never get a direct path to Postgres.

That is a good pattern at scale. It is **not** what we are doing for this ticket.

### Private subnet

A **private subnet** is a slice of your VCN where resources **do not get a public IP**.

- Nothing in that subnet is directly reachable from the internet.

### NAT Gateway

**NAT** = Network Address Translation.

A **NAT Gateway** lets resources in a **private** subnet make **outbound** internet calls (apt update, pull Docker images, call APIs) **without** being reachable inbound from the internet.

```text
Private subnet VM  →  NAT Gateway  →  Internet   (outbound OK)
Internet           ✗→  Private subnet VM          (inbound blocked)
```

Compare:

| | Public subnet + Internet Gateway | Private subnet + NAT |
|--|----------------------------------|----------------------|
| Public IP on VM | Yes | No |
| SSH/HTTPS from internet | Yes (if firewall allows) | No |
| VM can reach internet | Yes | Yes (via NAT) |

### What Nginx is

**Nginx** is a web server / reverse proxy that sits in front of your app and handles traffic from the internet.

Think of it as the **front door**:

```text
Internet (browsers, curl)
    → Nginx (ports 80 / 443)     ← public
        → Gunicorn (127.0.0.1:8000)  ← private, Django
            → Postgres / Redis
```

### What “only on 127.0.0.1:8000” means

Gunicorn is listening on **localhost only** — reachable **from inside the VM**, not from the public internet.

- `curl http://127.0.0.1:8000/...` on the VM → works  
- Someone on the internet hitting `http://132.226.88.147:8000/...` → should **not** work (and we don’t want that)

That’s intentional: don’t expose Gunicorn directly.

### What Nginx does for you

| Job | Why |
|-----|-----|
| Listen on **port 80** (HTTP) / **443** (HTTPS) | Normal web ports |
| Forward (“proxy”) requests to Gunicorn | Django still serves the API |
| Terminate HTTPS later (with Certbot) | TLS certificates live at Nginx |
| Optional static files, rate limits, etc. | Production hardening |

So when you open `http://132.226.88.147/api/v1/health/`:

1. Request hits **Nginx** on port 80  
2. Nginx forwards to **Gunicorn** on `127.0.0.1:8000`  
3. Django answers; Nginx sends the response back

### Analogy

- **Gunicorn** = kitchen (cooks the response)  
- **Nginx** = waiter at the door (takes orders from outside, talks to the kitchen)
